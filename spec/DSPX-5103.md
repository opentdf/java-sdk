# java-sdk: ZipReader/manifest parsing hangs or throws unchecked exceptions on malformed archives (isTDF / loadTDF)

## Summary
Java counterpart of DSPX-5102 (opentdf/platform#4202). The Go SDK panics on malformed archives passed to IsValidTdf / LoadTDF. The Java ZIP reader has the same root cause: sizes, offsets and lengths are read as signed values and never validated. In Java this surfaces as a hang or an unchecked exception escaping SDK.isTDF / loadTDF, rather than a panic.
Found by source inspection of java-sdk @ 57d070b0 (0.18.0). Paths are under sdk/src/main/java/io/opentdf/platform/sdk/. Not yet reproduced at runtime, except where noted as confirmed by reading the code.
Findings1. Infinite loop on a negative extra-field dataSize (DoS)ZipReader.java:262-283: int dataSize = readShort(); sign-extends, so 0xFFFC becomes -4. The end of each loop iteration runs zipChannel.position(fieldStart + dataSize + 4), which resets the position to fieldStart. The for loop then never advances. A 4-byte edit to any TDF's central directory hangs the reading thread. This is the most severe item here.
2. Negative lengths reach ByteBuffer.allocate / position()ZipReader.java:247,255: int fileNameLength = readShort(); turns a filename length above 32767 into a negative number, and ByteBuffer.allocate(negative) throws IllegalArgumentException. This is the closest analog of the Go makeslice panic.
ZipReader.java:270-276: a ZIP64 extra-field offset of 0xFFFFFFFFFFFFFFFF is read as -1. zipChannel.position(-1) (:167) then throws IllegalArgumentException.
ZipReader.java:133: the ZIP64 EOCD-locator offset is passed to position() without a check. A negative value throws the same way.
A ZIP64 size of -1 makes doneReading() return true immediately, so the manifest reads as "". Gson then fails. This is not a crash, but it produces a misleading error.
extraFieldLength and fileCommentLength also come from signed readShort().
3. No manifest size capTDFReader.java:43 reads the manifest entry into an unbounded ByteArrayOutputStream via transferTo. A huge declared size is limited only by the real file size, so a crafted multi-GB container can OOM the reader. Go caps the manifest with maxSize, and web-sdk caps it at 10 MB.
4. Unchecked exceptions escape isTDFSDK.isTDF (SDK.java:164-176) catches only IOException | InvalidZipException. Everything in items 1–2 propagates out of a method whose contract is to return a boolean. TDF.loadTDF (TDF.java:~567) does not wrap these exceptions either.
5. Null sub-fields in an assertion statementManifest.java:540,543: "format": null or "schema": null inside an assertion statement throws an unchecked UnsupportedOperationException from JsonNull.getAsString() during readManifest. "value": null is silently turned into the string "null". A top-level "statement": null is handled safely. Gson is case-sensitive, so the Go "Statement": null trick does not apply.
Out of scope hereThe reader trusting payload.isEncrypted = false (item 3 of the GitHub issue) is DSPX-4748. It is still present: TDF.java:580 skips unwrap, and :657/:667/:677-686 fall back to keyless SHA-256. isTDF only checks entry names, so it also accepts these files.
ZIP64 conformance (APPNOTE thresholds and field order) is DSPX-4589. This ticket covers robustness against hostile input only.
Proposed fixRead all 16- and 32-bit ZIP fields as unsigned (Short.toUnsignedInt, Integer.toUnsignedLong), and use explicit sentinel comparisons instead of == -1.
Reject any ZIP64 value above Long.MAX_VALUE, and any offset or offset+size beyond channel.size(), with InvalidZipException.
Require each extra-field iteration to advance, and check that dataSize fits within the remaining extraFieldLength. web-sdk's sliceExtraFields (zip-reader.ts:316-339) is a good model.
Cap the manifest size (match go/web), and use getAsJsonPrimitive-style null checks in Manifest deserializers.
Make isTDF return false for any parse failure, and have loadTDF throw an SDK exception.
Acceptance criteriaRegression tests for each input above. None may hang or throw an unchecked exception; isTDF returns false and loadTDF throws a typed SDK exception.
Add the shapes to the Jazzer corpus (DSPX-5070), and add a timeout so a hang is reported as a failure.
Cover them in the xtest structural-mutation suite (DSPX-4923) so go, java and web are held to the same "clean rejection" rule.

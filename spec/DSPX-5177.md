# Reduce buf.build (BSR) dependency when building opentdf/java-sdk from source

## Summary
ProblemBuilding opentdf/java-sdk from source fails often because the build hits Buf Schema Registry rate limits. This happens in xtest CI (xtest/sdk/java → make → mvn clean install), and it happened on a recent xtest run for opentdf/tests PR #571. The error looks like this:
[INFO]      [exec] Failure: resource_exhausted: too many requests
[INFO]      [exec]
[INFO]      [exec] Please see https://buf.build/docs/bsr/rate-limits/ for details about BSR rate limiting.When this happens, the whole xtest job fails for a reason unrelated to the change under test.
Why each build hits BSRIn sdk/pom.xml, the generate-sources phase runs buf generate twice, through maven-antrun-plugin:
buf generate https://github.com/opentdf/platform.git#branch=${platform.branch},subdir=service
buf generate buf.build/grpc-ecosystem/grpc-gateway
sdk/buf.gen.yaml uses remote plugins only, and each of them runs on BSR:
buf.build/protocolbuffers/java:v25.3
buf.build/connectrpc/kotlin
buf.build/grpc/java:v1.61.1
The module dependencies also come from BSR: bufbuild/protovalidate, googleapis/googleapis, and grpc-ecosystem/grpc-gateway.
The xtest workflow builds the Java CLI separately in every matrix job, once for each resolved java head. A single X-Test run can therefore make dozens of BSR calls in a short window, enough to hit the rate limit. xtest.yml runs bufbuild/buf-action with token: ${{ secrets.BUF_TOKEN }}, but we should confirm the token really authenticates the buf generate calls inside Maven. Authenticated limits are much higher than anonymous ones.
Proposed options (roughly in order of effort)[ ] Verify auth. Make sure BUF_TOKEN reaches the mvn step, either through buf registry login or a BUF_TOKEN env var, and that it is set for every caller (including fork PRs and dependabot runs, which don't get secrets).
[ ] Use local plugins in java-sdk. Generate code with locally run protoc-gen-java, protoc-gen-grpc-java, and protoc-gen-connect-kotlin instead of remote plugins. Possible approaches: binaries pulled from Maven Central through protobuf-maven-plugin / os-maven-plugin, or local: plugins in buf.gen.yaml. This removes remote plugin execution entirely and matches DSPX-4832, which already did the same for virtru-sdk-java in DSPX-4835.
[ ] Skip codegen entirely. Publish the platform's generated Java protos as a Maven artifact so source builds don't need codegen.
Acceptance criteriaA from-source java-sdk build in xtest does not fail because of BSR rate limits. Either it makes no BSR calls, or the calls are authenticated, cached, and retried.
xtest builds each java-sdk/platform pair at most once per workflow run.
RelatedDSPX-4832: Switch buf.gen.yaml from remote to local plugins (subtask DSPX-4835 covers virtru-sdk-java; opentdf/java-sdk is not included)
